## 6. Готовый рассказ на 1–2 минуты (от первого лица)

Я сделал WPF-приложение «Игра "Жизнь"» по паттерну MVVM. Проект разделён на три части. Модель `GameField` хранит двумерный массив клеток и реализует правила Конвея с восьмёрочным соседством; она ничего не знает про WPF. Для нового поколения я считаю результат в отдельный массив и только потом подменяю им текущий, иначе соседи считались бы по уже изменённым клеткам. Клетки за краем поля считаются мёртвыми, то есть это не тор.

ViewModel — это `MainViewModel` и `CellViewModel`. Они наследуют `ViewModelBase`, где реализован `INotifyPropertyChanged`: метод `SetField` записывает значение и сообщает интерфейсу об изменении, поэтому экран обновляется сам. Действия оформлены командами: у меня своя реализация `ICommand` — `RelayCommand`, которая принимает метод и условие `CanExecute`. Например, «Старт» доступен только при `!IsRunning`, «Стоп» — только при `IsRunning`, а во время симуляции блокируются правка клеток, шаг и импорт. Доступность перепроверяется автоматически через `CommandManager.RequerySuggested`.

View — `MainWindow.xaml`. В `DataContext` окна лежит `MainViewModel`, а привязки берут из неё размеры, плотность, интервал, счётчики и команды. Поле — это `ItemsControl` с `UniformGrid`, привязанный к `ObservableCollection` клеток. Каждая клетка — кнопка с общей командой и параметром `CommandParameter="{Binding}"`, а цвет живой клетки задаёт `DataTrigger` по `IsAlive` в стиле из `App.xaml`.

Непрерывный режим работает на `DispatcherTimer`: он тикает в UI-потоке и вызывает тот же метод, что и кнопка «Шаг»; интервал можно менять на лету. Состояние поля можно сохранить в JSON и загрузить обратно через `System.Text.Json` и стандартные диалоги; при плохом файле я показываю MessageBox, а не роняю программу. Code-behind окна почти пустой: только `InitializeComponent()` и установка `DataContext`.

### 7.1. Что такое MVVM и что делает каждый слой

MVVM — паттерн, который делит приложение на три слоя. **Model** — данные и бизнес-логика; у меня это `GameField` (`GameField.cs:14`): массив клеток и правила Конвея, без единой ссылки на WPF. **View** — то, что видит пользователь: `MainWindow.xaml` и `App.xaml`, только разметка, привязки и стили. **ViewModel** — «посредник»: `MainViewModel` (`MainViewModel.cs:20`) отдаёт View свойства (`Rows`, `Density`, `Generation`) и команды (`StartCommand`), а вызовы превращает в действия над моделью. Связка идёт через `DataContext` и привязки данных, поэтому ViewModel не знает про кнопки, а модель — про ViewModel. Плюс: логику можно тестировать без окна, а интерфейс менять, не трогая логику. Признак правильного MVVM у меня — пустой code-behind (`MainWindow.xaml.cs:22`).
```csharp
// View (XAML) -> Binding -> ViewModel -> вызывает -> Model
<Button Command="{Binding StartCommand}" />   // View
StartCommand = new RelayCommand(Start, () => !IsRunning);   // ViewModel
_field.NextGeneration();   // Model (вызывается из Advance)
```

### 7.2. Как настроены команды (RelayCommand, Execute, CanExecute, CanExecuteChanged, RequerySuggested)

`ICommand` — интерфейс с методами `Execute(object?)`, `CanExecute(object?)` и событием `CanExecuteChanged`. Готовой реализации в WPF нет, поэтому я написал `RelayCommand` (`RelayCommand.cs:16`): он хранит два делегата — `Action<object?> _execute` (`RelayCommand.cs:20`) и `Func<object?, bool>? _canExecute` (`RelayCommand.cs:23`); есть перегрузка для методов без параметра (`RelayCommand.cs:36`). Когда кнопка получает `Command="{Binding StartCommand}"`, WPF сам вызывает `CanExecute` и выключает кнопку при `false` (`IsEnabled = false`, а триггер в `App.xaml:79` делает её бледной). При клике вызывается `Execute` (`RelayCommand.cs:59`), который запускает метод ViewModel. Событие `CanExecuteChanged` (`RelayCommand.cs:47`) я не поднимаю вручную: подписка перенаправлена на статический `CommandManager.RequerySuggested`, который WPF вызывает при кликах, вводе с клавиатуры, смене фокуса — после этого все кнопки заново спрашивают `CanExecute`. Команды создаются в конструкторе (`MainViewModel.cs:163`–`MainViewModel.cs:179`), а к кнопкам привязаны в `MainWindow.xaml:52`–`MainWindow.xaml:88`.
```csharp
StartCommand = new RelayCommand(Start, () => !IsRunning);
StopCommand  = new RelayCommand(Stop,  () => IsRunning);
public bool CanExecute(object? p) => _canExecute is null || _canExecute(p);
public event EventHandler? CanExecuteChanged { add => CommandManager.RequerySuggested += value; remove => CommandManager.RequerySuggested -= value; }
```

### 7.3. Что случится, если убрать CanExecute; где он у меня и как блокирует кнопки при IsRunning

`CanExecute` я использую в конструкторе `MainViewModel` для восьми команд из девяти (`MainViewModel.cs:163`–`MainViewModel.cs:179`): везде `() => !IsRunning`, кроме «Стоп» (`() => IsRunning`); у «Экспорт» проверки нет. Пока `IsRunning == true` (ставится в `MainViewModel.cs:263`, сбрасывается в `MainViewModel.cs:272`), кнопки «Случайное заполнение», «Очистить», «Шаг», «Старт», «Импорт», «Пересоздать» и все клетки серые и не нажимаются, а «Стоп» и «Экспорт» активны. Если убрать `CanExecute`, кнопки останутся доступными всегда: во время симуляции можно было бы кликать клетки, вызывать «Шаг», очищать или импортировать поле, пока таймер сам меняет его, «Старт» можно было бы нажать повторно, а «Стоп» нажимался бы, когда останавливать нечего. Ничего не упадёт (метод просто выполнится), но нарушится требование задания — редактировать поле можно только до запуска или на паузе — и получится путаница. Без `CanExecute` пришлось бы вручную писать проверки `if (IsRunning) return;` в каждом методе и отдельно серить кнопки.
```csharp
ImportCommand = new RelayCommand(Import, () => !IsRunning);   // блокируется при работе
ExportCommand = new RelayCommand(Export);                      // canExecute не задан -> всегда true
```

### 7.4. INotifyPropertyChanged и что будет без него

`INotifyPropertyChanged` — интерфейс с одним событием `PropertyChanged`. Когда ViewModel меняет свойство, она поднимает это событие с именем свойства, а привязка (`{Binding}`) подписана на него и перечитывает значение. Без интерфейса привязка один раз прочитает значение при создании окна и дальше не узнает об изменениях: счётчик «Поколение» застынет на нуле, `IsAlive` не перекрасит клетку. У меня интерфейс реализован в `ViewModelBase` (`ViewModelBase.cs:13`): событие `ViewModelBase.cs:18`, метод `OnPropertyChanged` с `[CallerMemberName]` (`ViewModelBase.cs:23`) и универсальный `SetField<T>` (`ViewModelBase.cs:31`), который сравнивает значения (`EqualityComparer<T>`, `ViewModelBase.cs:34`) и уведомляет только при реальном изменении. Каждое свойство — полная форма: `get => _rows; set => SetField(ref _rows, ...)` (`MainViewModel.cs:67`). Для вычисляемого `AliveCount` (`MainViewModel.cs:122`) уведомление шлю вручную: `OnPropertyChanged(nameof(AliveCount))` (`MainViewModel.cs:211`). Для коллекции `Cells` роль такого интерфейса играет `ObservableCollection`. Реализация неявная — члены `public` в классе (явной реализации `ICommand.Execute` в стиле `void ICommand.Execute(...)` у меня нет).
```csharp
public int Generation { get => _generation; private set => SetField(ref _generation, value); }
```

### 7.5. DataContext и как найти источник привязки

`DataContext` — объект, в котором `{Binding Имя}` ищет свойство `Имя`. Он наследуется вниз по дереву элементов, если не переопределён. У меня он один раз устанавливается в конструкторе окна: `DataContext = new MainViewModel();` (`MainWindow.xaml.cs:22`), поэтому все привязки верхней панели и строки состояния читают `MainViewModel`. Исключение — шаблон клетки: внутри `DataTemplate` (`MainWindow.xaml:113`) `DataContext` становится элементом коллекции, то есть `CellViewModel`, поэтому `Command="{Binding ToggleCommand}"` берётся из `CellViewModel`, а не из `MainViewModel`. Чтобы найти источник любой привязки: 1) смотрю имя после `Binding`; 2) определяю `DataContext` в этом месте дерева (окно — `MainViewModel`, шаблон клетки — `CellViewModel`); 3) ищу свойство с таким именем в этом классе. Если привязка не работает, ошибка видна в окне Output Visual Studio («BindingExpression path error»). `Binding` без пути (`CommandParameter="{Binding}"`, `MainWindow.xaml:121`) означает сам `DataContext`.
```xml
<Button Command="{Binding ToggleCommand}" CommandParameter="{Binding}" />  <!-- внутри DataTemplate: DataContext = CellViewModel -->
```

### 7.6. Binding Mode и UpdateSourceTrigger

`Mode` — направление передачи: `OneWay` (ViewModel → экран), `TwoWay` (в обе стороны), `OneTime` (один раз), `OneWayToSource` (экран → ViewModel). Значение по умолчанию зависит от свойства: у `TextBox.Text` и `Slider.Value` это `TwoWay`, у `TextBlock.Text` — `OneWay`. У меня `Mode=OneWay` указан явно в строке состояния (`MainWindow.xaml:136`, `MainWindow.xaml:141`): у `AliveCount` и `Generation` нет публичного `set`, обратная запись не нужна. `UpdateSourceTrigger` — когда экран отдаёт значение ViewModel: `LostFocus` (по умолчанию для `TextBox`), `PropertyChanged` (сразу при каждом изменении), `Explicit` (вручную). В `TextBox` для строк и столбцов я поставил `UpdateSourceTrigger=PropertyChanged` (`MainWindow.xaml:42`, `MainWindow.xaml:47`), чтобы значение попадало в `Rows`/`Cols` при каждом нажатии клавиши и кнопка «Пересоздать поле» использовала свежее число, даже если фокус ещё в поле. У `Slider` триггер по умолчанию `PropertyChanged`, поэтому `Density` и `IntervalMs` обновляются, пока двигаю ползунок (`MainWindow.xaml:58`, `MainWindow.xaml:67`).
```xml
<TextBox Text="{Binding Rows, UpdateSourceTrigger=PropertyChanged}" />   <!-- TwoWay по умолчанию -->
<Run Text="{Binding Generation, Mode=OneWay}" />
```

### 7.6a. Trigger и DataTrigger

`Trigger` следит за свойством самого элемента: `IsMouseOver`, `IsEnabled`, `IsPressed`. У меня в `ControlButtonStyle` два таких: при наведении `Opacity 0.85`, при `IsEnabled=False` — `Opacity 0.4` (`App.xaml:79`). `DataTrigger` следит за данными — за значением привязки, то есть за свойством объекта из `DataContext`. В `CellButtonStyle` (`App.xaml:113`) он читает `{Binding IsAlive}` у `CellViewModel` и при `True` меняет `Background` на зелёный. Обычный `Trigger` не может смотреть на свойства ViewModel — для этого нужен именно `DataTrigger`. Работает потому, что `IsAlive` поднимает `PropertyChanged` через `SetField`. Порядок важен: триггеры перекрывают `Setter` стиля, поэтому базовый цвет белый, а зелёный накладывается сверху.
```xml
<DataTrigger Binding="{Binding IsAlive}" Value="True"><Setter Property="Background" Value="{StaticResource CellAliveBrush}" /></DataTrigger>
```

### 7.7. Стили и ресурсы: StaticResource и DynamicResource

Ресурс — объект в словаре `Resources` с ключом `x:Key` (кисти, стили). Я положил их в `Application.Resources` (`App.xaml`), поэтому они доступны всем окнам. Есть неявный стиль без ключа — `TargetType="Window"` — он применяется ко всем окнам автоматически, и именованные стили (`ControlButtonStyle`, `CellButtonStyle`, `PanelLabelStyle`), которые подключаются явно: `Style="{StaticResource ...}"`. `StaticResource` ищет ресурс один раз при загрузке XAML и подставляет значение; ресурс должен быть объявлен выше по файлу или в родительском словаре. Работает быстрее и используется у меня везде. `DynamicResource` подписывается на ресурс и подхватывает его замену во время работы (например, смену темы или системных цветов), но медленнее и нужен, только если ресурс меняется. У меня цвета не меняются, поэтому `DynamicResource` не нужен. Плюс стилей — единое оформление без копирования атрибутов: все кнопки панели выглядят одинаково благодаря `ControlButtonStyle`.
```xml
<SolidColorBrush x:Key="CellAliveBrush" Color="#FF2E7D32" />
<Button Style="{StaticResource CellButtonStyle}" />
```

### 7.8. ObservableCollection и List

`List<T>` при добавлении и удалении элементов ничего никому не сообщает, поэтому `ItemsControl` не узнает, что список изменился. `ObservableCollection<T>` реализует `INotifyCollectionChanged` и поднимает событие при `Add`, `Remove`, `Clear`, а `ItemsControl` на него подписан и сам добавляет или убирает визуальные элементы. У меня `Cells` — `ObservableCollection<CellViewModel>` (`MainViewModel.cs:60`). В `RebuildCells` (`MainViewModel.cs:189`) я делаю `Clear()` и `Add(...)` — поле на экране перестраивается автоматически. Важно: `ObservableCollection` сообщает только об изменении состава, а не об изменении полей внутри элементов. Поэтому у каждой клетки свой `INotifyPropertyChanged` (`IsAlive`).
```csharp
public ObservableCollection<CellViewModel> Cells { get; } = new();
Cells.Add(new CellViewModel(r, c, _field[r, c], ToggleCellCommand));
```

### 7.9. Почему клетка — отдельный CellViewModel

`ItemsControl` строит по одному `Button` на элемент коллекции, и каждой кнопке нужны собственные данные с уведомлением об изменении: `IsAlive` (для `DataTrigger`), координаты `Row`/`Col` и команда. В модели `GameField` клетки — просто `bool[,]`: у элемента массива нет события `PropertyChanged`, и привязаться к нему нельзя. Поэтому `CellViewModel` (`CellViewModel.cs:13`) — тонкая обёртка над клеткой: `Row`, `Col`, `IsAlive` (через `SetField`) и `ToggleCommand`. Синхронизация двусторонняя: при клике `ToggleCell` меняет и клетку, и модель (`MainViewModel.cs:221`), а после шага `SyncCellsFromField` (`MainViewModel.cs:208`) переписывает `IsAlive` из модели. Команда на все клетки общая (`MainViewModel.cs:194` передаёт `ToggleCellCommand`), поэтому не создаётся сотни `RelayCommand`. Альтернатива (`Button` с `Tag` и обработчиком `Click`) нарушала бы MVVM.
```csharp
public bool IsAlive { get => _isAlive; set => SetField(ref _isAlive, value); }
Cells.Add(new CellViewModel(r, c, _field[r, c], ToggleCellCommand));   // одна общая команда
```

### 7.10. DispatcherTimer и System.Timers.Timer / Threading.Timer (поток UI)

Элементы WPF можно менять только из UI-потока. `DispatcherTimer` создан для WPF: событие `Tick` приходит в UI-потоке через `Dispatcher`, поэтому в обработчике я напрямую меняю свойства, к которым привязан экран (`Generation`, `IsAlive`), и ничего дополнительно не нужно. `System.Timers.Timer` и `System.Threading.Timer` вызывают обработчик в потоке из пула; чтобы обновить интерфейс, пришлось бы писать `Dispatcher.Invoke(...)` или ловить `InvalidOperationException` («вызывающий поток не может получить доступ к этому объекту»). Минус `DispatcherTimer`: он не точнее обработки очереди UI — если шаг долгий, тики задерживаются. Для шага Жизни 60x60 это не проблема. Подписка — `+=` на `Tick` (`MainViewModel.cs:159`), запуск и остановка — `Start()` (`MainViewModel.cs:267`) и `Stop()` (`MainViewModel.cs:274`).
```csharp
_timer = new DispatcherTimer();
_timer.Tick += (_, _) => Advance();
_timer.Interval = TimeSpan.FromMilliseconds(IntervalMs); _timer.Start();
```

### 7.11. Почему code-behind пуст

Смысл MVVM в том, что View не содержит логики. В `MainWindow.xaml.cs` только `InitializeComponent()` (создаёт элементы из XAML) и `DataContext = new MainViewModel();` (`MainWindow.xaml.cs:22`). Обработчиков `Click`, `TextChanged` нет: кнопки работают через `Command`, поля через `Binding`, цвет клеток через `DataTrigger`. Благодаря этому логику можно проверить без окна, а разметку переделывать независимо. Код, связанный только с отображением (анимация, фокус), в code-behind допустим и не нарушает MVVM, но у меня такого нет. Вторая половина класса `MainWindow` (`partial`) генерируется из XAML при сборке.

### 7.12. Как сделан импорт и экспорт JSON

Файл читает и пишет `FieldJsonService` (`FieldJsonService.cs:13`), а диалог выбора файла и обработку ошибок делает `MainViewModel`. Двумерный массив в JSON неудобен, поэтому `GameField.ToFlatArray()` (`GameField.cs:81`) разворачивает его в одномерный построчно: индекс `r * Cols + c`. Этот массив кладётся в DTO `FieldDto` (`FieldJsonService.cs:22`) вместе с `Rows` и `Cols`, и `JsonSerializer.Serialize` (`FieldJsonService.cs:43`) с `WriteIndented = true` превращает его в текст, который пишется через `File.WriteAllText` в UTF-8. Импорт (`FieldJsonService.cs:48`) читает файл, делает `Deserialize<FieldDto>`, проверяет, что размеры положительные и `Cells.Length == Rows * Cols` (`FieldJsonService.cs:56`), создаёт `GameField` и заполняет его `LoadFrom`. Ошибки (`IOException`, `InvalidDataException`, `JsonException`) ловятся в `MainViewModel.Import` (`MainViewModel.cs:329`) и показываются `MessageBox`, программа не падает. Диалоги — `SaveFileDialog`/`OpenFileDialog` из `Microsoft.Win32`; `ShowDialog() != true` означает «Отмена».
```json
{ "Rows": 20, "Cols": 20, "Cells": [false, false, true, ...] }
```

### 7.13. Как реализованы правила Конвея и граничные клетки

Метод `NextGeneration` (`GameField.cs:144`) создаёт временный массив `next` (`GameField.cs:146`), для каждой клетки считает живых соседей через `CountAliveNeighbors` (`GameField.cs:116`) и применяет правило одной строкой (`GameField.cs:156`): `next[r, c] = alive ? neighbors is 2 or 3 : neighbors == 3;`. Живая клетка выживает при 2 или 3 соседях, мёртвая оживает при ровно 3, иначе клетка мертва. Временный массив нужен, чтобы все клетки считались по одному и тому же (текущему) поколению; в конце `_cells = next` (`GameField.cs:160`). Соседи — 8 клеток (сдвиги -1..1 по обеим осям, кроме (0,0)). Граница: условие `nr >= 0 && nr < Rows && nc >= 0 && nc < Cols` (`GameField.cs:128`) отбрасывает клетки за краем — они считаются мёртвыми, поэтому края поля «неактивны» и это не тор. `is 2 or 3` — шаблон C#: «равно 2 или 3».
```csharp
next[r, c] = alive ? neighbors is 2 or 3 : neighbors == 3;
```

### 7.14. Что изменилось бы для тора

На торе поле замкнуто: справа от последнего столбца снова идёт первый, под последней строкой — первая. Менять нужно только `CountAliveNeighbors`: вместо отбрасывания клеток за краем брать индексы по модулю. Правило в `NextGeneration` и весь остальной код остаются прежними. Так глайдер не упирается в стену, а летит по кругу бесконечно.
```csharp
int nr = (row + dr + Rows) % Rows;   // + Rows, чтобы не получить отрицательное число
int nc = (col + dc + Cols) % Cols;
if (_cells[nr, nc]) count++;          // проверка границ (if nr >= 0 ...) больше не нужна
```
Нюанс: на совсем крошечных полях (1–2 клетки) сосед мог бы совпасть с самой клеткой или посчитаться дважды; у меня минимум 5x5, поэтому проблемы нет.

### 7.16. Можно ли сделать асинхронный шаг (async/await + Task.Run) и зачем

Можно. Сейчас шаг синхронный и для 60x60 занимает доли миллисекунды (3600 клеток x 8 соседей), поэтому интерфейс не подвисает. Если бы поле было огромным, вычисление лучше вынести в фон: `await Task.Run(() => _field.NextGeneration());`, а после `await` продолжение выполняется снова в UI-потоке (в WPF есть контекст синхронизации), и там безопасно вызывать `SyncCellsFromField` и обновлять привязанные свойства. Обработчик тика тогда — `async void` или команда с `async Task`; надо защититься от повторного входа (пока шаг не завершён, следующий тик пропускать) и блокировать кнопки на время вычисления. Зачем: не блокировать UI-поток долгой работой. Оговорка: `Task.Run` нельзя использовать для изменения привязанных свойств внутри фонового потока, только для чистого вычисления модели. В моём проекте `async` не используется.
```csharp
private async Task AdvanceAsync()
{
    await Task.Run(() => _field.NextGeneration());   // считаем в пуле потоков
    SyncCellsFromField();                            // снова UI-поток
    Generation++;
}
```

### 7.17. Асинхронность и вопросы вокруг (экзаменационный вопрос 18)

**Любой ли метод может быть `async`?** Нет. `async` можно поставить на метод (в том числе лямбду и локальную функцию), который возвращает `void`, `Task`, `Task<T>` или `ValueTask`; свойство-геттер и конструктор нельзя (конструктор запускает асинхронную работу через фабричный метод). Без `await` внутри такой метод компилируется с предупреждением, но выполняется синхронно. **`Task` как `Promise`:** `Task<T>` — объект «обещание результата в будущем» (аналог `Promise` в JavaScript); `await` не блокирует поток, а «приостанавливает» метод до готовности результата, а исключение из задачи пробрасывается в месте `await`. `async void` допустим только для обработчиков событий: его исключения нельзя перехватить снаружи. `Task.Run` запускает работу в пуле потоков, `await` возвращает продолжение в исходный контекст (UI-поток в WPF). В проекте асинхронность не реализована (см. п. 8, вопрос 18).

### 7.18. Интерфейсы, делегаты, события, полиморфизм, SOLID (краткие ответы)

**Интерфейсы (6).** Интерфейс — контракт без реализации. В проекте реализованы `ICommand` (в `RelayCommand`, `RelayCommand.cs:16`) и `INotifyPropertyChanged` (в `ViewModelBase`, `ViewModelBase.cs:13`). Реализация неявная: члены объявлены `public` в классе. Явная (`void ICommand.Execute(...)`) — когда член доступен только через интерфейс и не виден у самого класса; у меня её нет. Свойства команд объявлены типом `ICommand` (`MainViewModel.cs:142`), а не `RelayCommand`: код зависит от абстракции.

**Делегаты (7).** Делегат — тип, описывающий сигнатуру метода. `Action<object?>` — метод с параметром без результата (`RelayCommand.cs:20`); `Func<object?, bool>` — метод с параметром и результатом `bool` (`RelayCommand.cs:23`). `Predicate<T>` — то же, что `Func<T, bool>`, но отдельный тип (в проекте не используется, вместо него `Func<object?, bool>`). В `RelayCommand` вторая перегрузка принимает `Action` и `Func<bool>` и оборачивает их лямбдами (`RelayCommand.cs:36`).

**События (12).** Событие — способ сказать «что-то произошло»: подписчики добавляются `+=`, отписываются `-=`. В проекте: `PropertyChanged` (`ViewModelBase.cs:18`), `CanExecuteChanged` с собственными `add`/`remove` (`RelayCommand.cs:47`), `Tick` таймера (`MainViewModel.cs:159`). Поднимаю событие безопасно: `PropertyChanged?.Invoke(...)`.

**Полиморфизм (5).** Один и тот же вызов ведёт себя по-разному в зависимости от реального типа. `StartCommand` объявлен как `ICommand`, но внутри лежит `RelayCommand`; WPF вызывает `Execute` через интерфейс. `MainViewModel` и `CellViewModel` наследуют `ViewModelBase` (абстрактный класс) и используют его `SetField`. Ещё пример — `MainWindow : Window`.

**SOLID.** S: `GameField` — правила, `FieldJsonService` — файл, `MainViewModel` — состояние экрана, `RelayCommand` — команды, `CellViewModel` — клетка. O: новую команду можно добавить, не меняя `RelayCommand`; частично, `MainViewModel` при этом всё равно правится. L: `MainViewModel` и `CellViewModel` подставимы вместо `ViewModelBase`; любой `ICommand` подойдёт кнопке. I: интерфейсы маленькие (`ICommand`, `INotifyPropertyChanged`), лишних методов реализовать не приходится. D: выполнено частично — `CellViewModel` получает `ICommand` снаружи (зависит от абстракции), но `MainViewModel` сам создаёт `new FieldJsonService()`, `new GameField()` и диалоги, то есть зависит от конкретных классов; для полного D нужны интерфейсы `IFieldStorage`, `IDialogService` и внедрение через конструктор (DI в проекте нет).
