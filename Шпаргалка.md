## 1. Перед защитой (за 5 минут)

1. Открыть терминал в папке проекта: `cd "D:\ТРПО\КостинДА_5пр"`.
2. Собрать: `dotnet build КостинДА_5пр.sln` — должно быть «Предупреждений: 0, Ошибок: 0».
3. Запустить один раз: `dotnet run --project Lab5\Lab5.csproj` — должно открыться окно «Игра "Жизнь" — Костин Д.А., ТРПО пр.5» с белой сеткой 20x20 и внизу «Готово. Задайте начальное состояние…». Закрыть окно.
4. Открыть в VS Code файлы, которые будете показывать (см. п. 2 и п. 5), — так не придётся искать их при преподавателе.
5. Если `dotnet` не найден — установить .NET 10 SDK (проект `net10.0-windows`, нужен именно Windows).

## 2. Как открыть проект

1. VS Code → File → Open Folder → `D:\ТРПО\КостинДА_5пр`.
2. В панели Explorer раскрыть `Lab5` и три папки: **Model** (`GameField.cs`), **ViewModel** (`ViewModelBase.cs`, `RelayCommand.cs`, `CellViewModel.cs`, `MainViewModel.cs`), **Services** (`FieldJsonService.cs`). Рядом лежат XAML: `App.xaml` (стили), `MainWindow.xaml` (окно) и почти пустой `MainWindow.xaml.cs`.
3. С чего начать рассказ: с `MainWindow.xaml.cs` (MainWindow.xaml.cs:15 — одна строка `DataContext = new MainViewModel()`), затем `MainWindow.xaml` (View), потом `MainViewModel.cs` (ViewModel), в конце `GameField.cs` (Model).
4. Комментарии в коде помечены метками `[MVVM]`, `[Команда]`, `[Binding]`, `[Стиль]`, `[Таймер]`, `[JSON]` — по ним легко ориентироваться.

## 6. Готовый рассказ на 1–2 минуты (от первого лица)

Пути ниже даны относительно корня `D:\ТРПО\КостинДА_5пр`, строки — по оригинальным файлам без комментариев.

Я сделал WPF-приложение «Игра "Жизнь"» по паттерну MVVM. Модель — класс `GameField` (`Lab5\Model\GameField.cs:9`): он хранит двумерный массив клеток `_cells` (`Lab5\Model\GameField.cs:11`), размеры в свойствах `Rows` и `Cols` (`Lab5\Model\GameField.cs:13`, `Lab5\Model\GameField.cs:14`) и ничего не знает про WPF. Правила Конвея реализует `NextGeneration` (`Lab5\Model\GameField.cs:119`): я считаю результат в отдельный массив `next` и только потом подменяю им текущий, иначе соседи считались бы по уже изменённым клеткам. Живых соседей по восьми направлениям считает `CountAliveNeighbors` (`Lab5\Model\GameField.cs:93`); клетки за краем поля считаются мёртвыми, то есть это не тор. Случайное заполнение делает `Randomize` (`Lab5\Model\GameField.cs:46`), а для JSON есть пара `ToFlatArray` (`Lab5\Model\GameField.cs:61`) и `LoadFrom` (`Lab5\Model\GameField.cs:76`) — они разворачивают массив в одномерный построчно и обратно.

ViewModel — это `MainViewModel` (`Lab5\ViewModel\MainViewModel.cs:15`) и `CellViewModel` (`Lab5\ViewModel\CellViewModel.cs:6`). Оба наследуют `ViewModelBase` (`Lab5\ViewModel\ViewModelBase.cs:7`), где реализован `INotifyPropertyChanged`: есть событие `PropertyChanged` (`Lab5\ViewModel\ViewModelBase.cs:9`), а метод `SetField` (`Lab5\ViewModel\ViewModelBase.cs:15`) записывает значение и сообщает интерфейсу об изменении, поэтому экран обновляется сам. У клетки — `Row` и `Col` (`Lab5\ViewModel\CellViewModel.cs:10`, `Lab5\ViewModel\CellViewModel.cs:11`), свойство `IsAlive` (`Lab5\ViewModel\CellViewModel.cs:13`) и общая для всех клеток `ToggleCommand` (`Lab5\ViewModel\CellViewModel.cs:19`). В `MainViewModel` живут свойства для привязок: `Rows` (`Lab5\ViewModel\MainViewModel.cs:38`) и `Cols` (`Lab5\ViewModel\MainViewModel.cs:44`) с ограничением 5..60, `Density` (`Lab5\ViewModel\MainViewModel.cs:50`), `IntervalMs` (`Lab5\ViewModel\MainViewModel.cs:56`), `Generation` (`Lab5\ViewModel\MainViewModel.cs:70`), `IsRunning` (`Lab5\ViewModel\MainViewModel.cs:76`), вычисляемый `AliveCount` (`Lab5\ViewModel\MainViewModel.cs:82`) и коллекция клеток `Cells` типа `ObservableCollection` (`Lab5\ViewModel\MainViewModel.cs:36`).

Действия оформлены командами. У меня своя реализация `ICommand` — `RelayCommand` (`Lab5\ViewModel\RelayCommand.cs:10`): она хранит делегат действия `_execute` (`Lab5\ViewModel\RelayCommand.cs:12`) и необязательное условие `_canExecute` (`Lab5\ViewModel\RelayCommand.cs:13`). Событие `CanExecuteChanged` (`Lab5\ViewModel\RelayCommand.cs:27`) перенаправлено на `CommandManager.RequerySuggested`, поэтому доступность кнопок перепроверяется автоматически. Команды создаются в конструкторе `MainViewModel` (`Lab5\ViewModel\MainViewModel.cs:107`–`Lab5\ViewModel\MainViewModel.cs:115`): `ToggleCellCommand` (`Lab5\ViewModel\MainViewModel.cs:107`, метод клика `ToggleCell` — `Lab5\ViewModel\MainViewModel.cs:146`), `RandomizeCommand` (`Lab5\ViewModel\MainViewModel.cs:108`), `StepCommand` (`Lab5\ViewModel\MainViewModel.cs:110`, метод `Advance` — `Lab5\ViewModel\MainViewModel.cs:180`), `StartCommand` (`Lab5\ViewModel\MainViewModel.cs:111`), `StopCommand` (`Lab5\ViewModel\MainViewModel.cs:112`), `ExportCommand` (`Lab5\ViewModel\MainViewModel.cs:113`), `ImportCommand` (`Lab5\ViewModel\MainViewModel.cs:114`) и `ResizeFieldCommand` (`Lab5\ViewModel\MainViewModel.cs:115`, метод `ResizeField` — `Lab5\ViewModel\MainViewModel.cs:172`). «Старт» доступен только при `!IsRunning`, «Стоп» — только при `IsRunning`, а во время симуляции блокируются правка клеток, шаг и импорт.

Непрерывный режим работает на `DispatcherTimer` (`Lab5\ViewModel\MainViewModel.cs:22`, создаётся на `Lab5\ViewModel\MainViewModel.cs:104`): событие `Tick` (`Lab5\ViewModel\MainViewModel.cs:105`) тикает в UI-потоке и вызывает тот же `Advance`, что и кнопка «Шаг»; интервал можно менять на лету — это делает сеттер `IntervalMs` (`Lab5\ViewModel\MainViewModel.cs:62`). Состояние поля сохраняется и загружается через `FieldJsonService` (`Lab5\Services\FieldJsonService.cs:9`): метод `Export` (`Lab5\Services\FieldJsonService.cs:21`) кладёт данные в DTO `FieldDto` (`Lab5\Services\FieldJsonService.cs:14`) и пишет их через `System.Text.Json`, а `Import` (`Lab5\Services\FieldJsonService.cs:34`) проверяет размеры и длину массива. Диалоги и обработку ошибок делают `Export` (`Lab5\ViewModel\MainViewModel.cs:203`) и `Import` (`Lab5\ViewModel\MainViewModel.cs:224`) во ViewModel: при плохом файле я показываю MessageBox (`Lab5\ViewModel\MainViewModel.cs:247`), а не роняю программу.

View — `MainWindow.xaml`. В конструкторе окна одна значимая строка `DataContext = new MainViewModel()` (`Lab5\MainWindow.xaml.cs:15`), поэтому все привязки берут данные из `MainViewModel`: размеры (`Lab5\MainWindow.xaml:23`, `Lab5\MainWindow.xaml:26`), плотность (`Lab5\MainWindow.xaml:31`), интервал (`Lab5\MainWindow.xaml:35`), кнопки с `Command="{Binding StartCommand}"` (`Lab5\MainWindow.xaml:43`) и счётчики `AliveCount` и `Generation` (`Lab5\MainWindow.xaml:76`, `Lab5\MainWindow.xaml:79`). Поле — это `ItemsControl` (`Lab5\MainWindow.xaml:54`) с панелью `UniformGrid` (`Lab5\MainWindow.xaml:57`), привязанный к `Cells`. Каждая клетка — кнопка из `DataTemplate` (`Lab5\MainWindow.xaml:61`) с общей командой `ToggleCommand` и параметром `CommandParameter="{Binding}"` (`Lab5\MainWindow.xaml:65`). Оформление лежит в `App.xaml`: стиль кнопок `ControlButtonStyle` (`Lab5\App.xaml:24`) с обычными `Trigger` (`Lab5\App.xaml:44`–`Lab5\App.xaml:49`) и стиль клетки `CellButtonStyle` (`Lab5\App.xaml:54`), где `DataTrigger` по `IsAlive` (`Lab5\App.xaml:70`) красит живую клетку в зелёный. Таким образом code-behind почти пустой: только `InitializeComponent()` и установка `DataContext`.

### 7.1. Что такое MVVM и что делает каждый слой

MVVM — паттерн, который делит приложение на три слоя. **Model** — данные и бизнес-логика; у меня это `GameField` (`GameField.cs:9`): массив клеток и правила Конвея, без единой ссылки на WPF. **View** — то, что видит пользователь: `MainWindow.xaml` и `App.xaml`, только разметка, привязки и стили. **ViewModel** — «посредник»: `MainViewModel` (`MainViewModel.cs:15`) отдаёт View свойства (`Rows`, `Density`, `Generation`) и команды (`StartCommand`), а вызовы превращает в действия над моделью. Связка идёт через `DataContext` и привязки данных, поэтому ViewModel не знает про кнопки, а модель — про ViewModel. Плюс: логику можно тестировать без окна, а интерфейс менять, не трогая логику. Признак правильного MVVM у меня — пустой code-behind (`MainWindow.xaml.cs:15`).
```csharp
// View (XAML) -> Binding -> ViewModel -> вызывает -> Model
<Button Command="{Binding StartCommand}" />   // View
StartCommand = new RelayCommand(Start, () => !IsRunning);   // ViewModel
_field.NextGeneration();   // Model (вызывается из Advance)
```

### 7.2. Как настроены команды (RelayCommand, Execute, CanExecute, CanExecuteChanged, RequerySuggested)

`ICommand` — интерфейс с методами `Execute(object?)`, `CanExecute(object?)` и событием `CanExecuteChanged`. Готовой реализации в WPF нет, поэтому я написал `RelayCommand` (`RelayCommand.cs:10`): он хранит два делегата — `Action<object?> _execute` (`RelayCommand.cs:12`) и `Func<object?, bool>? _canExecute` (`RelayCommand.cs:13`); есть перегрузка для методов без параметра (`RelayCommand.cs:22`). Когда кнопка получает `Command="{Binding StartCommand}"`, WPF сам вызывает `CanExecute` и выключает кнопку при `false` (`IsEnabled = false`, а триггер в `App.xaml:47` делает её бледной). При клике вызывается `Execute` (`RelayCommand.cs:35`), который запускает метод ViewModel. Событие `CanExecuteChanged` (`RelayCommand.cs:27`) я не поднимаю вручную: подписка перенаправлена на статический `CommandManager.RequerySuggested`, который WPF вызывает при кликах, вводе с клавиатуры, смене фокуса — после этого все кнопки заново спрашивают `CanExecute`. Команды создаются в конструкторе (`MainViewModel.cs:107`–`MainViewModel.cs:115`), а к кнопкам привязаны в `MainWindow.xaml:28`–`MainWindow.xaml:46`.
```csharp
StartCommand = new RelayCommand(Start, () => !IsRunning);
StopCommand  = new RelayCommand(Stop,  () => IsRunning);
public bool CanExecute(object? p) => _canExecute is null || _canExecute(p);
public event EventHandler? CanExecuteChanged { add => CommandManager.RequerySuggested += value; remove => CommandManager.RequerySuggested -= value; }
```

### 7.3. Что случится, если убрать CanExecute; где он у меня и как блокирует кнопки при IsRunning

`CanExecute` я использую в конструкторе `MainViewModel` для восьми команд из девяти (`MainViewModel.cs:107`–`MainViewModel.cs:115`): везде `() => !IsRunning`, кроме «Стоп» (`() => IsRunning`); у «Экспорт» проверки нет. Пока `IsRunning == true` (ставится в `MainViewModel.cs:190` внутри `Start`, сбрасывается в `MainViewModel.cs:199` внутри `Stop`), кнопки «Случайное заполнение», «Очистить», «Шаг», «Старт», «Импорт», «Пересоздать» и все клетки серые и не нажимаются, а «Стоп» и «Экспорт» активны. Если убрать `CanExecute`, кнопки останутся доступными всегда: во время симуляции можно было бы кликать клетки, вызывать «Шаг», очищать или импортировать поле, пока таймер сам меняет его, «Старт» можно было бы нажать повторно, а «Стоп» нажимался бы, когда останавливать нечего. Ничего не упадёт (метод просто выполнится), но нарушится требование задания — редактировать поле можно только до запуска или на паузе — и получится путаница. Без `CanExecute` пришлось бы вручную писать проверки `if (IsRunning) return;` в каждом методе и отдельно серить кнопки.
```csharp
ImportCommand = new RelayCommand(Import, () => !IsRunning);   // блокируется при работе
ExportCommand = new RelayCommand(Export);                      // canExecute не задан -> всегда true
```

### 7.4. INotifyPropertyChanged и что будет без него

`INotifyPropertyChanged` — интерфейс с одним событием `PropertyChanged`. Когда ViewModel меняет свойство, она поднимает это событие с именем свойства, а привязка (`{Binding}`) подписана на него и перечитывает значение. Без интерфейса привязка один раз прочитает значение при создании окна и дальше не узнает об изменениях: счётчик «Поколение» застынет на нуле, `IsAlive` не перекрасит клетку. У меня интерфейс реализован в `ViewModelBase` (`ViewModelBase.cs:7`): событие `ViewModelBase.cs:9`, метод `OnPropertyChanged` с `[CallerMemberName]` (`ViewModelBase.cs:11`) и универсальный `SetField<T>` (`ViewModelBase.cs:15`), который сравнивает значения (`EqualityComparer<T>`, `ViewModelBase.cs:17`) и уведомляет только при реальном изменении. Каждое свойство — полная форма: `get => _rows; set => SetField(ref _rows, ...)` (`MainViewModel.cs:41`). Для вычисляемого `AliveCount` (`MainViewModel.cs:82`) уведомление шлю вручную: `OnPropertyChanged(nameof(AliveCount))` (`MainViewModel.cs:143`). Для коллекции `Cells` роль такого интерфейса играет `ObservableCollection`. Реализация неявная — члены `public` в классе (явной реализации `ICommand.Execute` в стиле `void ICommand.Execute(...)` у меня нет).
```csharp
public int Generation { get => _generation; private set => SetField(ref _generation, value); }
```

### 7.5. DataContext и как найти источник привязки

`DataContext` — объект, в котором `{Binding Имя}` ищет свойство `Имя`. Он наследуется вниз по дереву элементов, если не переопределён. У меня он один раз устанавливается в конструкторе окна: `DataContext = new MainViewModel();` (`MainWindow.xaml.cs:15`), поэтому все привязки верхней панели и строки состояния читают `MainViewModel`. Исключение — шаблон клетки: внутри `DataTemplate` (`MainWindow.xaml:61`) `DataContext` становится элементом коллекции, то есть `CellViewModel`, поэтому `Command="{Binding ToggleCommand}"` берётся из `CellViewModel`, а не из `MainViewModel`. Чтобы найти источник любой привязки: 1) смотрю имя после `Binding`; 2) определяю `DataContext` в этом месте дерева (окно — `MainViewModel`, шаблон клетки — `CellViewModel`); 3) ищу свойство с таким именем в этом классе. Если привязка не работает, ошибка видна в окне Output Visual Studio («BindingExpression path error»). `Binding` без пути (`CommandParameter="{Binding}"`, `MainWindow.xaml:65`) означает сам `DataContext`.
```xml
<Button Command="{Binding ToggleCommand}" CommandParameter="{Binding}" />  <!-- внутри DataTemplate: DataContext = CellViewModel -->
```

### 7.6. Binding Mode и UpdateSourceTrigger

`Mode` — направление передачи: `OneWay` (ViewModel → экран), `TwoWay` (в обе стороны), `OneTime` (один раз), `OneWayToSource` (экран → ViewModel). Значение по умолчанию зависит от свойства: у `TextBox.Text` и `Slider.Value` это `TwoWay`, у `TextBlock.Text` — `OneWay`. У меня `Mode=OneWay` указан явно в строке состояния (`MainWindow.xaml:76`, `MainWindow.xaml:79`): у `AliveCount` и `Generation` нет публичного `set`, обратная запись не нужна. `UpdateSourceTrigger` — когда экран отдаёт значение ViewModel: `LostFocus` (по умолчанию для `TextBox`), `PropertyChanged` (сразу при каждом изменении), `Explicit` (вручную). В `TextBox` для строк и столбцов я поставил `UpdateSourceTrigger=PropertyChanged` (`MainWindow.xaml:23`, `MainWindow.xaml:26`), чтобы значение попадало в `Rows`/`Cols` при каждом нажатии клавиши и кнопка «Пересоздать поле» использовала свежее число, даже если фокус ещё в поле. У `Slider` триггер по умолчанию `PropertyChanged`, поэтому `Density` и `IntervalMs` обновляются, пока двигаю ползунок (`MainWindow.xaml:31`, `MainWindow.xaml:35`).
```xml
<TextBox Text="{Binding Rows, UpdateSourceTrigger=PropertyChanged}" />   <!-- TwoWay по умолчанию -->
<Run Text="{Binding Generation, Mode=OneWay}" />
```

### 7.6a. Trigger и DataTrigger

`Trigger` следит за свойством самого элемента: `IsMouseOver`, `IsEnabled`, `IsPressed`. У меня в `ControlButtonStyle` два таких: при наведении `Opacity 0.85`, при `IsEnabled=False` — `Opacity 0.4` (`App.xaml:44`–`App.xaml:49`). `DataTrigger` следит за данными — за значением привязки, то есть за свойством объекта из `DataContext`. В `CellButtonStyle` (`App.xaml:70`) он читает `{Binding IsAlive}` у `CellViewModel` и при `True` меняет `Background` на зелёный. Обычный `Trigger` не может смотреть на свойства ViewModel — для этого нужен именно `DataTrigger`. Работает потому, что `IsAlive` поднимает `PropertyChanged` через `SetField`. Порядок важен: триггеры перекрывают `Setter` стиля, поэтому базовый цвет белый, а зелёный накладывается сверху.
```xml
<DataTrigger Binding="{Binding IsAlive}" Value="True"><Setter Property="Background" Value="{StaticResource CellAliveBrush}" /></DataTrigger>
```

### 7.7. Стили и ресурсы: StaticResource и DynamicResource

Ресурс — объект в словаре `Resources` с ключом `x:Key` (кисти, стили). Я положил их в `Application.Resources` (`App.xaml`), поэтому они доступны всем окнам. Есть неявный стиль без ключа — `TargetType="Window"` — он применяется ко всем окнам автоматически, и именованные стили (`ControlButtonStyle`, `CellButtonStyle`, `PanelLabelStyle`), которые подключаются явно: `Style="{StaticResource ...}"`. `StaticResource` ищет ресурс один раз при загрузке XAML и подставляет значение; ресурс должен быть объявлен выше по файлу или в родительском словаре. Работает быстрее и используется у меня везде. `DynamicResource` подписывается на ресурс и подхватывает его замену во время работы (например, смену темы или системных цветов), но медленнее и нужен, только если ресурс меняется. У меня цвета не меняются, поэтому `DynamicResource` не нужен. Плюс стилей — единое оформление без копирования атрибутов: все кнопки панели выглядят одинаково благодаря `ControlButtonStyle`.
```xml
<SolidColorBrush x:Key="CellAliveBrush" Color="#FF2E7D32" />
<Button Style="{StaticResource CellButtonStyle}" />
```

### 7.8. ObservableCollection и List

`List<T>` при добавлении и удалении элементов ничего никому не сообщает, поэтому `ItemsControl` не узнает, что список изменился. `ObservableCollection<T>` реализует `INotifyCollectionChanged` и поднимает событие при `Add`, `Remove`, `Clear`, а `ItemsControl` на него подписан и сам добавляет или убирает визуальные элементы. У меня `Cells` — `ObservableCollection<CellViewModel>` (`MainViewModel.cs:36`). В `RebuildCells` (`MainViewModel.cs:121`) я делаю `Clear()` (`MainViewModel.cs:123`) и `Add(...)` (`MainViewModel.cs:128`) — поле на экране перестраивается автоматически. Важно: `ObservableCollection` сообщает только об изменении состава, а не об изменении полей внутри элементов. Поэтому у каждой клетки свой `INotifyPropertyChanged` (`IsAlive`).
```csharp
public ObservableCollection<CellViewModel> Cells { get; } = new();
Cells.Add(new CellViewModel(r, c, _field[r, c], ToggleCellCommand));
```

### 7.9. Почему клетка — отдельный CellViewModel

`ItemsControl` строит по одному `Button` на элемент коллекции, и каждой кнопке нужны собственные данные с уведомлением об изменении: `IsAlive` (для `DataTrigger`), координаты `Row`/`Col` и команда. В модели `GameField` клетки — просто `bool[,]`: у элемента массива нет события `PropertyChanged`, и привязаться к нему нельзя. Поэтому `CellViewModel` (`CellViewModel.cs:6`) — тонкая обёртка над клеткой: `Row`, `Col`, `IsAlive` (через `SetField`) и `ToggleCommand`. Синхронизация двусторонняя: при клике `ToggleCell` меняет и клетку, и модель (`MainViewModel.cs:151`), а после шага `SyncCellsFromField` (`MainViewModel.cs:140`) переписывает `IsAlive` из модели. Команда на все клетки общая (`MainViewModel.cs:128` передаёт `ToggleCellCommand`), поэтому не создаётся сотни `RelayCommand`. Альтернатива (`Button` с `Tag` и обработчиком `Click`) нарушала бы MVVM.
```csharp
public bool IsAlive { get => _isAlive; set => SetField(ref _isAlive, value); }
Cells.Add(new CellViewModel(r, c, _field[r, c], ToggleCellCommand));   // одна общая команда
```

### 7.10. DispatcherTimer и System.Timers.Timer / Threading.Timer (поток UI)

Элементы WPF можно менять только из UI-потока. `DispatcherTimer` создан для WPF: событие `Tick` приходит в UI-потоке через `Dispatcher`, поэтому в обработчике я напрямую меняю свойства, к которым привязан экран (`Generation`, `IsAlive`), и ничего дополнительно не нужно. `System.Timers.Timer` и `System.Threading.Timer` вызывают обработчик в потоке из пула; чтобы обновить интерфейс, пришлось бы писать `Dispatcher.Invoke(...)` или ловить `InvalidOperationException` («вызывающий поток не может получить доступ к этому объекту»). Минус `DispatcherTimer`: он не точнее обработки очереди UI — если шаг долгий, тики задерживаются. Для шага Жизни 60x60 это не проблема. Подписка — `+=` на `Tick` (`MainViewModel.cs:105`), запуск и остановка — `Start()` (`MainViewModel.cs:188`, `_timer.Start()` на `MainViewModel.cs:192`) и `Stop()` (`MainViewModel.cs:196`, `_timer.Stop()` на `MainViewModel.cs:198`).
```csharp
_timer = new DispatcherTimer();
_timer.Tick += (_, _) => Advance();
_timer.Interval = TimeSpan.FromMilliseconds(IntervalMs); _timer.Start();
```

### 7.11. Почему code-behind пуст

Смысл MVVM в том, что View не содержит логики. В `MainWindow.xaml.cs` только `InitializeComponent()` (создаёт элементы из XAML) и `DataContext = new MainViewModel();` (`MainWindow.xaml.cs:15`). Обработчиков `Click`, `TextChanged` нет: кнопки работают через `Command`, поля через `Binding`, цвет клеток через `DataTrigger`. Благодаря этому логику можно проверить без окна, а разметку переделывать независимо. Код, связанный только с отображением (анимация, фокус), в code-behind допустим и не нарушает MVVM, но у меня такого нет. Вторая половина класса `MainWindow` (`partial`) генерируется из XAML при сборке.

### 7.12. Как сделан импорт и экспорт JSON

Файл читает и пишет `FieldJsonService` (`FieldJsonService.cs:9`), а диалог выбора файла и обработку ошибок делает `MainViewModel`. Двумерный массив в JSON неудобен, поэтому `GameField.ToFlatArray()` (`GameField.cs:61`) разворачивает его в одномерный построчно: индекс `r * Cols + c`. Этот массив кладётся в DTO `FieldDto` (`FieldJsonService.cs:14`) вместе с `Rows` и `Cols`, и `JsonSerializer.Serialize` (`FieldJsonService.cs:30`) с `WriteIndented = true` превращает его в текст, который пишется через `File.WriteAllText` в UTF-8. Импорт (`FieldJsonService.cs:34`) читает файл, делает `Deserialize<FieldDto>`, проверяет, что размеры положительные и `Cells.Length == Rows * Cols` (`FieldJsonService.cs:40`), создаёт `GameField` и заполняет его `LoadFrom`. Ошибки (`IOException`, `InvalidDataException`, `JsonException`) ловятся в `MainViewModel.Import` (`MainViewModel.cs:245`) и показываются `MessageBox`, программа не падает. Диалоги — `SaveFileDialog`/`OpenFileDialog` из `Microsoft.Win32`; `ShowDialog() != true` означает «Отмена».
```json
{ "Rows": 20, "Cols": 20, "Cells": [false, false, true, ...] }
```

### 7.13. Как реализованы правила Конвея и граничные клетки

Метод `NextGeneration` (`GameField.cs:119`) создаёт временный массив `next` (`GameField.cs:121`), для каждой клетки считает живых соседей через `CountAliveNeighbors` (`GameField.cs:93`) и применяет правило одной строкой (`GameField.cs:129`): `next[r, c] = alive ? neighbors is 2 or 3 : neighbors == 3;`. Живая клетка выживает при 2 или 3 соседях, мёртвая оживает при ровно 3, иначе клетка мертва. Временный массив нужен, чтобы все клетки считались по одному и тому же (текущему) поколению; в конце `_cells = next` (`GameField.cs:133`). Соседи — 8 клеток (сдвиги -1..1 по обеим осям, кроме (0,0)). Граница: условие `nr >= 0 && nr < Rows && nc >= 0 && nc < Cols` (`GameField.cs:104`) отбрасывает клетки за краем — они считаются мёртвыми, поэтому края поля «неактивны» и это не тор. `is 2 or 3` — шаблон C#: «равно 2 или 3».
```csharp
next[r, c] = alive ? neighbors is 2 or 3 : neighbors == 3;
```

### 7.14. Что изменилось бы для тора

На торе поле замкнуто: справа от последнего столбца снова идёт первый, под последней строкой — первая. Менять нужно только `CountAliveNeighbors`: вместо отбрасывания клеток за краем брать индексы по модулю. Правило в `NextGeneration` и весь остальной код остаются прежними. Так глайдер не упирается в стену, а летит по кругу бесконечно.
```csharp
int nr = (row + dr + Rows) % Rows;   // + Rows, чтобы не получить отрицательное число
int nc = (col + dc + Cols) % Cols;
if (_cells[nr, nc]) count++;          // проверка границ (if nr >= 0 ...) больше не нужна
```
Нюанс: на совсем крошечных полях (1–2 клетки) сосед мог бы совпасть с самой клеткой или посчитаться дважды; у меня минимум 5x5, поэтому проблемы нет.

Вариант с тренажёром слов (WordsTrainerApp) уже сдан другим студентом по этому курсу, и мне не хотелось повторять чужое приложение. «Игра "Жизнь"» есть в списке вариантов задания, поэтому согласовывать её отдельно не требовалось. К тому же она хорошо показывает все требуемые элементы: `ItemsControl` с большим числом однотипных элементов и `DataTrigger` по `IsAlive`, команды с настоящим `CanExecute` (блокировка при симуляции), `DispatcherTimer`, JSON. ### 7.16. Можно ли сделать асинхронный шаг (async/await + Task.Run) и зачем

Можно. Сейчас шаг синхронный и для 60x60 занимает доли миллисекунды (3600 клеток x 8 соседей), поэтому интерфейс не подвисает. Если бы поле было огромным, вычисление лучше вынести в фон: `await Task.Run(() => _field.NextGeneration());`, а после `await` продолжение выполняется снова в UI-потоке (в WPF есть контекст синхронизации), и там безопасно вызывать `SyncCellsFromField` и обновлять привязанные свойства. Обработчик тика тогда — `async void` или команда с `async Task`; надо защититься от повторного входа (пока шаг не завершён, следующий тик пропускать) и блокировать кнопки на время вычисления. Зачем: не блокировать UI-поток долгой работой. Оговорка: `Task.Run` нельзя использовать для изменения привязанных свойств внутри фонового потока, только для чистого вычисления модели. В моём проекте `async` не используется.
```csharp
private async Task AdvanceAsync()
{
    await Task.Run(() => _field.NextGeneration());   // считаем в пуле потоков
    SyncCellsFromField();                            // снова UI-поток
    Generation++;
}
```

### 7.17. Асинхронность и вопросы вокруг (экзаменационный вопрос 18)

**Любой ли метод может быть `async`?** Нет. `async` можно поставить на метод (в том числе лямбду и локальную функцию), который возвращает `void`, `Task`, `Task<T>` или `ValueTask`; свойство-геттер и конструктор нельзя (конструктор запускает асинхронную работу через фабричный метод). Без `await` внутри такой метод компилируется с предупреждением, но выполняется синхронно. **`Task` как `Promise`:** `Task<T>` — объект «обещание результата в будущем» (аналог `Promise` в JavaScript); `await` не блокирует поток, а «приостанавливает» метод до готовности результата, а исключение из задачи пробрасывается в месте `await`. `async void` допустим только для обработчиков событий: его исключения нельзя перехватить снаружи. `Task.Run` запускает работу в пуле потоков, `await` возвращает продолжение в исходный контекст (UI-поток в WPF). В проекте асинхронность не реализована (см. п. 8, вопрос 18).

### 7.18. Интерфейсы, делегаты, события, полиморфизм, SOLID (краткие ответы)

**Интерфейсы (6).** Интерфейс — контракт без реализации. В проекте реализованы `ICommand` (в `RelayCommand`, `RelayCommand.cs:10`) и `INotifyPropertyChanged` (в `ViewModelBase`, `ViewModelBase.cs:7`). Реализация неявная: члены объявлены `public` в классе. Явная (`void ICommand.Execute(...)`) — когда член доступен только через интерфейс и не виден у самого класса; у меня её нет. Свойства команд объявлены типом `ICommand` (`MainViewModel.cs:94`), а не `RelayCommand`: код зависит от абстракции.

**Делегаты (7).** Делегат — тип, описывающий сигнатуру метода. `Action<object?>` — метод с параметром без результата (`RelayCommand.cs:12`); `Func<object?, bool>` — метод с параметром и результатом `bool` (`RelayCommand.cs:13`). `Predicate<T>` — то же, что `Func<T, bool>`, но отдельный тип (в проекте не используется, вместо него `Func<object?, bool>`). В `RelayCommand` вторая перегрузка принимает `Action` и `Func<bool>` и оборачивает их лямбдами (`RelayCommand.cs:22`).

**События (12).** Событие — способ сказать «что-то произошло»: подписчики добавляются `+=`, отписываются `-=`. В проекте: `PropertyChanged` (`ViewModelBase.cs:9`), `CanExecuteChanged` с собственными `add`/`remove` (`RelayCommand.cs:27`), `Tick` таймера (`MainViewModel.cs:105`). Поднимаю событие безопасно: `PropertyChanged?.Invoke(...)`.

**Полиморфизм (5).** Один и тот же вызов ведёт себя по-разному в зависимости от реального типа. `StartCommand` объявлен как `ICommand`, но внутри лежит `RelayCommand`; WPF вызывает `Execute` через интерфейс. `MainViewModel` и `CellViewModel` наследуют `ViewModelBase` (абстрактный класс) и используют его `SetField`. Ещё пример — `MainWindow : Window`.

**SOLID.** S: `GameField` — правила, `FieldJsonService` — файл, `MainViewModel` — состояние экрана, `RelayCommand` — команды, `CellViewModel` — клетка. O: новую команду можно добавить, не меняя `RelayCommand`; частично, `MainViewModel` при этом всё равно правится. L: `MainViewModel` и `CellViewModel` подставимы вместо `ViewModelBase`; любой `ICommand` подойдёт кнопке. I: интерфейсы маленькие (`ICommand`, `INotifyPropertyChanged`), лишних методов реализовать не приходится. D: выполнено частично — `CellViewModel` получает `ICommand` снаружи (зависит от абстракции), но `MainViewModel` сам создаёт `new FieldJsonService()`, `new GameField()` и диалоги, то есть зависит от конкретных классов; для полного D нужны интерфейсы `IFieldStorage`, `IDialogService` и внедрение через конструктор (DI в проекте нет).
